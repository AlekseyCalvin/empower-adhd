# Reference: Google Developer Documentation Style Guide Highlights

This document provides a comprehensive reference for technical writing style, adapted from the Google Developer Documentation Style Guide for clean, direct, and accessible technical communication.

## 1. Tone, Voice, and Person

### Voice and Tone
- **Conversational, friendly, and direct**: Write like a knowledgeable, helpful engineer speaking to a peer.
- **Active voice**: Make the actor clear. Place the subject before the verb.
  - *Do*: "The parser generates an Abstract Syntax Tree (AST)."
  - *Don't*: "An Abstract Syntax Tree (AST) is generated by the parser."
  - *Exception*: Use passive voice when the actor is irrelevant or unknown (e.g., "The cache was cleared at midnight").
- **Second person**: Address the developer as *you*, and use imperative verbs for instructions.
  - *Do*: "To install the dependencies, run `npm install`."
  - *Don't*: "We can install the dependencies..." or "The user installs..."

### Politeness and Punctuation
- **Avoid *please* in instructions**: In technical documentation, *please* adds conversational bloat.
  - *Do*: "To open the configuration file, select **Settings > Config**."
  - *Don't*: "Please open the configuration file..."
- **No exclamation marks**: Maintain a calm, professional tone. Avoid artificial excitement.
- **Avoid filler and meta-announcements**: Cut "Let's take a look at...", "Note that...", "At this point in time...".

## 2. Sentence Structure and Procedures

### Conditions and Goals First
State the circumstance, condition, or goal *before* the instruction so the reader can evaluate relevance immediately.

| Recommended | Not Recommended |
|---|---|
| To delete the database, click **Delete**. | Click **Delete** to delete the database. |
| For more information, see [Authentication Guide](https://example.com). | See [Authentication Guide](https://example.com) for more information. |
| If you deploy to AWS, set the `REGION` environment variable. | Set the `REGION` environment variable if you deploy to AWS. |

### Procedural Step Structure
1. **One action per step**: Keep numbered steps atomic.
2. **State location before action**:
   - *Do*: "In the project root, open `config.yaml`."
   - *Don't*: "Open `config.yaml` in the project root."
3. **Action before result**:
   - *Do*: "Click **Save**. The dashboard updates with the new metric."
   - *Don't*: "The dashboard updates when you click **Save**."
4. **Mark optional steps clearly**:
   - *Do*: "1. Optional: Add a custom description."
   - *Don't*: "1. (Optional) Add a custom description."

## 3. Lists and Formatting

### List Selection
- **Numbered lists (`1., 2., 3.`)**: Use strictly for ordered sequences, chronological procedures, or prioritized items.
- **Bulleted lists (`- `)**: Use for unordered sets, non-sequential options, or collections of equal weight.
- **Description lists (`- **Term**: definition`)**: Use for definitions, parameters, error codes, and key-value attributes.

### List Parallelism and Punctuation
- Maintain grammatical parallelism across all items (all imperative verbs, all noun phrases, or all full sentences).
- Start each item with a capital letter.
- If items are complete sentences or contain verbs, end with a period. If items are short fragments or noun lists, omit end punctuation consistently.

---

## 4. Code and UI Formatting

- **Code font (`backticks`)**: Use for file names (`main.py`), function names (`parseQuery()`), variables (`user_id`), HTTP methods (`GET`), CLI commands (`git status`), and configuration keys (`max_connections`).
- **Bold (`**bold**`)**: Use for UI elements, buttons, menu paths, and tab names (e.g., "Click **Apply Changes**", "**File > Export**").
- **Placeholders**: Use uppercase snake case or uppercase descriptive tokens (e.g., `api_key=YOUR_API_KEY` or `git checkout BRANCH_NAME`).

---

## 5. Avoiding Excessive Claims and Jargon

- **Factual, verifiable statements**: Avoid superlatives (*best*, *fastest*, *seamless*, *guaranteed*, *flawless*).
  - *Do*: "PostgreSQL handles 10,000 queries per second in this benchmark."
  - *Don't*: "PostgreSQL provides industry-leading, lightning-fast performance."
- **Demystify or replace jargon**: Use precise terms over buzzwords.
  - Replace *blast radius* with *impact scope*.
  - Replace *ingest* with *import* or *load*.
  - Replace *out-of-the-box* with *pre-configured* or *built-in*.
- **Timeless documentation**: Avoid temporal markers like *currently*, *new in 2026*, *soon*, or *recently*.
