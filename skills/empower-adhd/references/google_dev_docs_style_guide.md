# Google Developer Documentation Style Guide: Core Principles and Formatting

This reference document compiles the core writing, grammar, formatting, and structural guidelines from the Google Developer Documentation Style Guide for clear, precise, and accessible technical communication.

---

## 1. Tone, Voice, and Person

### Voice and Tone
- **Conversational, friendly, and direct**: Write like a knowledgeable, professional engineer explaining concepts to a peer. Avoid condescension, pedantry, slang, or frivolous humor.
- **Active voice**: Make the subject performing the action explicit. Place the actor before the verb.
  - *Recommended*: "The parser generates an Abstract Syntax Tree (AST)."
  - *Not Recommended*: "An Abstract Syntax Tree (AST) is generated by the parser."
  - *Exceptions*: Passive voice is acceptable when:
    1. Emphasizing the object over the actor (e.g., "The configuration file is saved automatically.").
    2. De-emphasizing the actor in error scenarios (e.g., "Three merge conflicts were detected in `main.go`" rather than "You caused three merge conflicts.").
    3. The actor is unknown or irrelevant (e.g., "The cache was cleared at midnight.").
- **Second person**: Address the developer as *you* or *your*. Use imperative verbs for instructions.
  - *Recommended*: "To configure the webhook, open `webhook.json`."
  - *Not Recommended*: "Let us configure the webhook..." or "The user configures the webhook..."
  - *First person plural (`we`, `our`)*: Use only when referring strictly to the maintainers, organization, or platform (e.g., "We recommend using TLS 1.3.").

### Politeness and Punctuation
- **Omit *please* in instructions**: In developer documentation and CLI instructions, *please* creates unnecessary conversational filler.
  - *Recommended*: "To view the dashboard, click **Metrics**."
  - *Not Recommended*: "To view the dashboard, please click **Metrics**."
- **Avoid exclamation marks**: Maintain a calm, authoritative, and objective tone. Do not use exclamation points to convey artificial enthusiasm.
- **Tone Examples**:

| Too Informal | Just Right | Too Formal |
|---|---|---|
| "Dude! This API is super awesome and fast!" | "This API lets you stream real-time telemetry with sub-millisecond latency." | "The API documented herein facilitates the acquisition of telemetry metrics in an expeditious manner." |
| "Then BOOM! Just garbage-collect and you're golden." | "To reclaim allocated memory, call `collectGarbage()`." | "Please note that successful termination of the operation necessitates the invocation of the automated memory management routine." |

## 2. Sentence Structure and Tense

### Conditions and Goals Preceding Instructions
Always state the condition, circumstance, or goal *before* the instruction. This allows the reader to immediately evaluate whether the instruction applies to them before reading the command.

| Recommended | Not Recommended |
|---|---|
| "To delete the database instance, click **Delete**." | "Click **Delete** to delete the database instance." |
| "For authentication configuration, see the [OAuth Guide](https://example.com)." | "See the [OAuth Guide](https://example.com) for authentication configuration." |
| "If you deploy to GCP, set the `PROJECT_ID` environment variable." | "Set the `PROJECT_ID` environment variable if you deploy to GCP." |
| "If your application runs in multiple regions, using global endpoints might add latency:" | "Using global endpoints might add latency if your application runs in multiple regions:" |

### Tense and Timelessness
- **Present tense**: Write in the present tense to describe software capabilities, system behavior, and user actions.
  - *Recommended*: "The service authenticates incoming tokens against the identity provider."
  - *Not Recommended*: "The service will authenticate incoming tokens against the identity provider."
- **Timeless documentation**: Avoid temporal markers that anchor content to a specific moment or require continuous maintenance.
  - Avoid words like: *now*, *currently*, *new*, *recently*, *in modern versions*, *in the future*.
  - *Recommended*: "The SDK supports streaming gRPC connections."
  - *Not Recommended*: "The SDK now supports streaming gRPC connections."
  - *Recommended*: "The following command-line flags are unsupported:"
  - *Not Recommended*: "The following command-line flags are not currently supported:"

### Articles, Contractions, and Prepositions
- **Include standard articles (*a*, *an*, *the*)**: Never omit articles for artificial brevity, including in section headings.
  - *Recommended*: "Create a VM instance"
  - *Not Recommended*: "Create VM instance"
- **Use standard two-word contractions**: Use natural contractions (*you're*, *don't*, *can't*, *it's*) to sustain a conversational tone.
  - Negation contractions (*don't*, *isn't*, *can't*) help prevent readers from missing a standalone "not".
  - Avoid nonstandard or three-word contractions (*mightn't've*, *there'd've*).
- **Prepositions**: Placing a preposition at the end of a sentence is natural in modern English when it improves readability.
  - *Recommended*: "Select the network interface you want to bind to."
  - *Not Recommended*: "Select the network interface to which you want to bind."

## 3. Headings and Document Organization

### Heading Capitalization and Syntax
- **Sentence case**: Capitalize only the first letter of the heading and any proper nouns. Never use Title Case.
  - *Recommended*: `## Configure your database connection`
  - *Not Recommended*: `## Configure Your Database Connection`
- **Descriptive, task-oriented headings**: Use imperative verbs for procedural sections and noun phrases for conceptual references.
  - *Procedural*: `## Create an API key`
  - *Conceptual*: `## Authentication architecture`
  - *Avoid generic headings*: Do not use standalone headings like `## Overview`, `## Introduction`, `## General`, or `## Next steps` without descriptive qualifiers.
- **Heading hierarchy**: Maintain strict nesting (`# H1` -> `## H2` -> `### H3` -> `#### H4`). Never skip heading levels.

## 4. Procedures and Numbered Steps

### Anatomy of a Procedural Step
To document complex procedural instructions, use the following sequence:

1. **Describe the action** (using an imperative verb).
2. **State the location before the action** (e.g., "In the left navigation menu, click...").
3. **Provide the command or code block** (if applicable).
4. **Explain placeholders used in the command**.
5. **State the expected result or output** (in a separate sentence or output block).
6. **Provide justifications if necessary** (why the step is needed).

### Procedural Step Examples

```markdown
1. In the Google Cloud console, go to the **Storage** page.
2. To create a bucket, click **Create bucket**.
3. For **Bucket name**, enter a globally unique identifier:
   ```bash
   gcloud storage buckets create gs://BUCKET_NAME --location=LOCATION
   ```
   Replace the following:
   - `BUCKET_NAME`: The unique name for your Cloud Storage bucket.
   - `LOCATION`: The target regional location (for example, `us-central1`).
   
   The console displays the newly provisioned bucket in the bucket list.
```

### Procedural Rules and Edge Cases
- **Single-step procedures**: If a procedure contains only one step, format it as a single sentence bullet point, not a numbered list.
  - *Recommended*:
    - "To clear the application cache, click **Flush Cache**."
  - *Not Recommended*:
    1. "Click **Flush Cache** to clear the application cache."
- **Sequential actions**: Combine minor related menu selections using angle brackets (`>`).
  - *Recommended*: "Click **File > New > Project**."
- **Optional steps**: Prepend the step with *Optional:* followed by a colon.
  - *Recommended*: "1. Optional: Specify a custom timeout in seconds."
  - *Not Recommended*: "1. (Optional) Specify a custom timeout in seconds."
- **Sub-steps**: Use nested alphabetical lists (`a., b., c.`) or nested Roman numerals (`i., ii., iii.`) for granular sub-actions.

## 5. Lists and Tables

### Choosing List Types
- **Numbered lists (`1., 2., 3.`)**: Use strictly for ordered sequences, chronological procedures, or prioritized workflows.
- **Bulleted lists (`- `)**: Use for unordered collections, feature sets, or interchangeable options.
- **Description lists (`- **Term**: Definition`)**: Use for glossaries, parameters, config options, or term-definition pairs.

### List Parallelism and Punctuation Rules
- **Parallel grammatical structure**: All items in a list must share the same grammatical form (e.g., all imperative verbs, all noun phrases, or all full sentences).
- **Capitalization**: Start every list item with a capital letter.
- **Punctuation**:
  - If list items are complete sentences or contain verbs, end every item with a period.
  - If list items are single words, short noun phrases without verbs, or code expressions, omit end periods consistently across the list.
- **Introductory sentences**: Precede lists with a complete introductory sentence ending with a colon. Never use a sentence fragment that is completed by the list items.
  - *Recommended*: "The SDK supports the following authentication methods:"
  - *Not Recommended*: "The SDK supports:"

### Tables vs. Lists
- Use **tables** when comparing multiple attributes across three or more entities, or presenting structured row-column matrices.
- Use **description lists** for simple term-definition pairs.
- Always include descriptive column headers for tables. Avoid empty table cells; use *None* or *Not applicable* instead.

## 6. Notices and Callouts

Use notices sparingly. If everything is emphasized, nothing is noticed.

| Notice Type | Syntax | Purpose |
|---|---|---|
| **Note** | `> [!NOTE]` | Highlights helpful supplementary information, tips, or edge-case context. |
| **Caution** | `> [!CAUTION]` | Warns against actions that could cause data loss, performance degradation, or unexpected behavior. |
| **Warning** | `> [!WARNING]` | Alerts the reader to critical hazards, security vulnerabilities, or irreversible destructive operations. |

- Never embed essential procedural steps inside a notice block.
- Place notices immediately *after* the paragraph or step to which they relate.

## 7. Cross-References and Markdown Links

- **Descriptive link text**: Always make the link text describe the destination resource. Never use generic link text like *here*, *link*, *this document*, or raw URLs.
  - *Recommended*: "For detailed schema options, see the [PostgreSQL Connection Guide](https://example.com/db)."
  - *Not Recommended*: "For detailed schema options, click [here](https://example.com/db)."
- **Link placement**: Integrate links smoothly into sentences without disrupting syntactic flow.

## 8. Numbers, Dates, Times, and Units

- **Numerals vs. words**:
  - Use Arabic numerals (`1`, `2`, `10`, `450`) for technical specifications, measurements, percentages, and UI counts.
  - Spell out numbers zero through nine only when used in non-technical, colloquial narrative prose.
- **Dates and times**:
  - Use unambiguous date formats: `YYYY-MM-DD` (ISO 8601) or spelled-out month names (`August 19, 2026`). Never use ambiguous numeric formats like `08/19/26` or `19/08/26`.
  - Specify the UTC offset or explicit timezone abbreviation (`2026-08-19T14:30:00Z` or `14:30 UTC`).
- **Units of measurement**: Include a non-breaking space between the numeral and unit abbreviation (e.g., `10 MB`, `250 ms`, `4 GHz`).

## 9. Hyphens, Abbreviations, and Acronyms

### Hyphenation Rules
- **Compound adjectives**: Hyphenate compound adjectives that precede a noun to avoid ambiguity.
  - *Recommended*: "client-side validation", "real-time telemetry", "open-source software", "two-way handshake".
  - *Do not hyphenate when following the noun*: "Validation happens on the client side.", "The telemetry runs in real time."
- **Prefixes**: Generally do not hyphenate standard prefixes (`multithreaded`, `microservices`, `prerequisite`, `subcommand`, `nonblocking`) unless needed to prevent mispronunciation or confusion with another word (e.g., `re-create` vs `recreate`, `co-locate`).

### Abbreviations and Acronyms
- **First reference expansion**: On first mention in a document or major section, spell out the full term followed by the acronym in parentheses.
  - *Recommended*: "The Abstract Syntax Tree (AST) represents..."
  - *Exceptions*: Widely recognized industry acronyms (API, CPU, HTTP, HTML, URL, JSON, SQL, CLI) do not require expansion.
- **Avoid obscure Latin abbreviations**:
  - Replace *e.g.,* with *for example,* or *such as*.
  - Replace *i.e.,* with *that is,* or *specifically*.
  - Replace *etc.* with a clear introductory phrase (*such as*, *including*).

## 10. Inclusive, Accessible, and Global Technical Writing

### Inclusive Language
- Use gender-neutral pronouns (*they*, *their*, *them*) when referring to hypothetical individuals.
- Avoid ableist metaphors (e.g., replace *sanity check* with *smoke test* or *preliminary check*; replace *blind spot* with *unmonitored area*).
- Replace violent or oppressive terminology:
  - Replace *master/slave* with *primary/replica* or *leader/follower*.
  - Replace *whitelist/blacklist* with *allowlist/denylist*.
  - Replace *kill* with *terminate*, *stop*, or *close*.

### Accessibility and Translation
- **No directional language**: Never use spatial orienting words (*above*, *below*, *on the left*, *top-right*). Use semantic references (e.g., "in the preceding code sample", "in the following table", "in the **Settings** sidebar").
- **Clear antecedents**: Avoid ambiguous pronouns (*this*, *that*, *it*) at the start of a sentence. Specify what "this" refers to (e.g., "This configuration parameter enables..." instead of "This enables...").
- **Plain English**: Keep sentence structures straightforward to assist translation engines and non-native English speakers.
